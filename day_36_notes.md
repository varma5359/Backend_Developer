## 7. Implementation

```python
# profiles/admin.py
from django.contrib import admin
from .models import Employee

@admin.register(Employee)
class EmployeeAdmin(admin.ModelAdmin):
    list_display = (
        "employee_code",
        "full_name",
        "email",
        "salary",
        "is_active",
    )
    search_fields = ("employee_code", "full_name", "email")
    list_filter = ("is_active", "joining_date")
    ordering = ("full_name",)

# config/urls.py normally already contains:
# path("admin/", admin.site.urls),
```

**Important:** If a code section says "add inside the existing model", paste it inside that class with the correct indentation. Do not create duplicate model classes or put model fields at module level. Preserve code from earlier days.

## 8. Deep concept explanation

### What is Django admin?
It is a built-in management interface for trusted staff. Django uses model metadata to generate forms and list pages. It saves time for internal data management and prototyping.

### Why must a model be registered?
Django admin does not automatically display every model. Register a model using `admin.site.register(Employee)` or the decorator shown in this lesson.

### @admin.register(Employee)
This decorator registers Employee with the admin site and associates it with EmployeeAdmin. The class defines how the changelist and forms behave.

### list_display
Controls which columns appear on the model's list page. Use actual model field names or methods. A misspelled name causes a system check error.

### search_fields
Adds search boxes over selected fields. It supports appropriate lookup behavior based on field types.

### list_filter
Adds sidebar filters. Choose fields that make sense for narrowing the list, such as is_active or joining_date.

### ordering
Sets the default sort order. A field name sorts ascending; prefix with "-" for descending.

### Superuser and staff
A superuser has all permissions. A staff user can access admin when is_staff is true, but their model permissions still determine what they can do. Avoid giving every user superuser privileges.

### Admin versus public website
Admin is for authorized site management. A public employee portal should have its own views, forms, templates and authorization rules. Hiding a link is not access control.

### Troubleshooting
- Model missing from admin: check model import, app registration and decorator.
- Admin login fails: check superuser credentials and authentication migrations.
- Field error: confirm list_display/search_fields/list_filter refer to valid fields.
- Admin 404: inspect config/urls.py for admin.site.urls.
- Static styles missing: inspect static-file configuration and browser network requests.

## 12. Troubleshooting

| Symptom | Likely reason | What to inspect |
|---|---|---|
| Model import fails | Wrong app/module name | Check profiles/models.py and app registration |
| Table does not exist | Migrations not applied | showmigrations and migrate |
| IntegrityError | Unique, required or foreign-key constraint failed | Inspect field values and referenced rows |
| DoesNotExist | get() returned no match | Verify lookup value or use filter when zero matches are expected |
| MultipleObjectsReturned | get() matched multiple rows | Use a unique lookup or filter |
| ProtectedError | PROTECT blocked deletion | Check related records and business rule |
| RelatedObjectDoesNotExist | One-to-one object not created | Create the related profile before accessing it |
| Query returns unexpected data | Wrong lookup or relationship | Inspect filters and actual records |

# Extended Beginner Lab — Django Admin Customization

## 19. What is Django admin?

Django admin is a built-in interface for trusted staff users to manage application records.

It can provide:
- List pages.
- Add forms.
- Change forms.
- Search.
- Filters.
- Read-only fields.
- Actions.
- Relationship selection.

It is useful for internal administration. It is not automatically the correct public-facing interface for customers or students.

## 20. Register a model

Example:

~~~python
from django.contrib import admin
from .models import Employee

admin.site.register(Employee)
~~~

This registers Employee with the admin site.

Django uses a default admin interface for the model.

## 21. Use the decorator form

An alternative is:

~~~python
@admin.register(Employee)
class EmployeeAdmin(admin.ModelAdmin):
    pass
~~~

The decorator registers the model with the custom ModelAdmin class.

Do not register the same model twice.

## 22. list_display

list_display controls which fields appear as columns in the list page.

~~~python
class EmployeeAdmin(admin.ModelAdmin):
    list_display = (
        "employee_code",
        "full_name",
        "department",
        "is_active",
    )
~~~

Use fields that help staff identify records.

Avoid displaying sensitive information such as password hashes or private tokens.

## 23. list_filter

list_filter adds sidebar filters.

~~~python
list_filter = (
    "department",
    "is_active",
)
~~~

This helps staff narrow a large record list.

## 24. search_fields

search_fields adds a search box.

~~~python
search_fields = (
    "employee_code",
    "full_name",
    "email",
)
~~~

For related fields, Django supports lookup paths using double underscores.

Example:

~~~python
search_fields = ("department__name",)
~~~

The related field must exist in the model relationship.

## 25. ordering

ordering controls the default order of records in the admin list.

~~~python
ordering = ("full_name",)
~~~

Use a stable ordering where appropriate.

## 26. readonly_fields

readonly_fields displays fields without allowing normal editing through the admin form.

~~~python
readonly_fields = (
    "created_at",
    "updated_at",
)
~~~

Use this for timestamps and values that should be managed by the application.

## 27. fieldsets

fieldsets organize fields into sections in the change form.

Example:

~~~python
fieldsets = (
    ("Employee details", {
        "fields": (
            "employee_code",
            "full_name",
            "department",
        )
    }),
    ("Status", {
        "fields": (
            "is_active",
        )
    }),
)
~~~

Every field name must exist on the model.

## 28. list_per_page

list_per_page controls how many records are displayed on one admin page.

Example:

~~~python
list_per_page = 25
~~~

This improves usability for large lists.

## 29. Admin actions

An admin action can apply an operation to selected records.

Example:

~~~python
@admin.action(description="Mark selected employees active")
def mark_active(modeladmin, request, queryset):
    queryset.update(is_active=True)
~~~

Then register the action in the ModelAdmin class.

Only create bulk actions when the business behavior is safe and clear.

## 30. Why admin actions need care

A bulk update may bypass custom model save() methods and signals for each instance.

If business logic must run for every record, use a carefully designed operation rather than blindly calling queryset.update().

Test bulk actions on practice data.

## 31. Admin authentication and permissions

The admin site requires a user with staff access and appropriate permissions.

is_staff allows access to the admin site, subject to permissions.

A superuser has all permissions by default.

Do not make every registered user a staff user or superuser.

## 33. Admin versus custom application pages

| Django admin | Custom application UI |
|---|---|
| Internal staff tool | User-facing workflow |
| Generated from model configuration | Designed for a specific user journey |
| Fast to set up | More design and code required |
| Uses Django admin permissions | Uses application-specific access rules |
| Useful for trusted data maintenance | Useful for students, customers and external users |

## 34. Common admin errors

|---|---|---|
| Model missing from admin | Not registered or app not installed | Check admin.py and INSTALLED_APPS |

## 46. Why queryset.update() matters

A bulk action may use queryset.update().

This executes a direct database update.

It does not call each model instance's save() method.

If the application relies on custom save logic or signals, a bulk update may skip that behavior.

Understand the side effects before using bulk actions.

## 50. Custom display method

A ModelAdmin can display a method.

Example:

~~~python
@admin.display(description="Employee status")
def status_label(self, obj):
    return "Active" if obj.is_active else "Inactive"
~~~

Then add status_label to list_display.

Use this when a display value is derived from model data.

The method should not perform an expensive database query for every row.

## 51. Admin list performance

If list_display accesses related objects, repeated queries can occur.

For a related field, consider ModelAdmin.get_queryset() with select_related().

Example:

~~~python
def get_queryset(self, request):
    queryset = super().get_queryset(request)
    return queryset.select_related("department")
~~~

Only add this when the model has the department relationship and the admin list uses it.

Measure behavior with representative data.
